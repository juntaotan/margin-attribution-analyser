## Step-based acceptance and full-flow example

Acceptance follows the computational sequence below. Each step must execute a concrete instance and assert its outputs before the next step consumes them. Use the same fixture throughout, then execute it once through the complete workflow. The supporting checks below and applicable FGW child acceptance requirements remain mandatory; they are not alternative acceptance stages.

| Step | Executable instance | Required evidence |
| --- | --- | --- |
| 1. Build period CSR | Explicit sales, issue and supporting records for both periods → existing period graph construction. | Actual recorded relationships, financial values and source mappings; retain the defined synthetic COGS node only in discovery. No supplied final CSR substitutes for construction. |
| 2. Discover abnormal branches | Generated period graphs → threshold preparation, upward propagation and original-path reconstruction. | A steel-cost difference path reaches product A under the existing threshold rules. Record selected boundaries, original positions and effective thresholds. Do not require symmetric replacement detection from the current actual-side discovery. |
| 3. Restore production trees | Branch evidence → actual/comparable production selection → top-down scope → bottom-up actual attribution. | Separate P0/P1 trees with seven occurrences and six edges each, explicit source links/shares, complete scope/evidence and costs 240/270. |
| 4. Prepare embeddings | Final trees → twelve-field contexts → configured real model. | Fourteen occurrence mappings, finite 384-dimensional vectors, verified inputs, neighbour alignment and model/template/runtime provenance. Preserve distinct occurrences when canonical inputs share vectors. |
| 5. Execute FGW | Eligible P0/P1 trees and generated vectors → prescribed standard solver. | One planned/executed pair; correspondence, separate objective terms, applied updates, fresh gap and truthful terminal/backend status. |
| 6. Execute the complete instance | One workflow invocation from the original records through FGW and financial evidence. | The preceding outputs are connected by stable identities without substituting prepared graphs/trees or synthetic embeddings. Compare the captured numerical inputs with independent CPU/POT references. |

Use explicitly passed fixture records and deterministic in-memory data providers for algorithm-library acceptance. Exercise the actual construction/orchestration path; providers must implement both terminal lookups and complete-instance loading from these records. Database-backed integration and HTTP tests, where applicable, supplement this instance rather than supplying its data. The real embedding provider is configured separately and must not be replaced by a deterministic vector stub in the full-flow acceptance run. Record unavailable model/runtime prerequisites as unverified.

### Shared full-flow fixture

The [shared fixture](Analysis_Fixture.md) owns the two seven-node enclosure batches, material context and original issue/output/processing evidence. Run each step from its relevant original records, then run one complete invocation. The following assertions apply to this confirmed full-flow test.

#### Final assertions and accuracy evidence

- P0/P1 each has seven occurrences, six production edges, one A root and complete declared topology/lineage/cost evidence. Synthetic `__COGS__` is absent from comparison trees.
- Root material subtotal is 220/250, labour 12/12, overhead 8/8, complete total 240/270 and per-output cost 24/27. Complete-total output discrepancy is zero in both periods; the preserved material-only output discrepancy is 20 in each, not zero.
- Steel quantity is unchanged at 20 kg and amount rises by 20; coating quantity is unchanged at 5 kg while R4 is replaced by R5 and its amount rises by 10. Total production-cost difference is 30 NZD. Do not describe the replacement as approved substitution or price/usage evidence as causal proof.
- Exactly one P0/P1 pair is planned and executed. Original evidence, context manifests and correspondence map back to distinct occurrence/production/issue/output/allocation identities.
- Capture the real model vectors and final CSR as immutable numerical inputs. Run independent CPU/POT validation under the child specifications' objective, feasible-start and FP64 `1e-8` requirements; check intermediate matrices, objective values, finite/nonnegative transport, marginal errors, directional derivatives, line-search behaviour and fresh terminal gap. For tied OT optima compare objective/marginals rather than demanding identical matrices. Do not assume independently initialised nonconvex solves must reach the same optimum.
- Human-labelled semantic correspondences are A↔A, S1↔S1, S2↔S2, R1↔R1, R2↔R2, R3↔R3 and R4↔R5. Report assigned mass and row-normalised shares against these labels, attribute distances and structure costs. Calibrate and freeze model-specific quality thresholds before claiming semantic acceptance; no fixed FGW score or semantic PASS threshold is invented here. Until calibrated, numerical/financial acceptance can pass while semantic quality remains unverified.
- Record model/revision/template/normalisation/precision, effective thresholds, numerical settings/starts, execution backend, actual/expected values, maximum errors and PASS/FAIL/unverified outcomes for each step and the complete invocation. Determine and freeze discovery thresholds against existing frontier semantics before execution acceptance; never change its rules to force the expected path.

The real-model full-flow fixture supplements, and never replaces, the existing fixed FGW regression or tree boundary fixtures. Use it on each execution path in scope with truthful device/fallback evidence. No model inference, solver execution or device validation is established by adding this specification.


## Supporting implementation and validation checks

1. Extract domain contracts/ports and inject Java frontier/FGW engines. Implement the independent CPU workflow and new endpoint without changing existing mathematical behaviour or public endpoints.
2. Test end-to-end graph-to-path-to-instance-to-pair mappings with explicitly passed in-memory fixtures; use isolated warehouse fixtures for applicable data-access integration, including no-path short-circuiting, candidate discovery in both periods, full-instance loading across dates, same-material distinct occurrences, all-pairs enumeration and missing evidence/vectors. Check zero/one-ID groups, exactly three pairs for three IDs, exactly 4,950 planned pairs for 100 IDs of one product, deduplication across periods/paths, no self/reverse duplicates, separation of products/namespaces and retained rejection statuses. The 100-ID count check tests enumeration and does not require 4,950 numerical solves in that fixture. Apply all production-tree grouping/evidence checks required by its specification when that behaviour is changed.
3. Test direct Java calls and HTTP/stream adapters against the same workflow results. Test invalid thresholds/topology, cancellation, numerical/eligibility failures and truthful per-stage backend reporting. Validate any frontend changes using the prescribed build plus required behavioural checks.
4. Implement contextual embedding preparation after final tree construction. Test all twelve fields, root/intermediate/leaf coverage, incoming/outgoing direction, aligned multiple-neighbour lists, valid empty lists, missing supplier/cost/descriptions, explicit source-kind and cost-basis handling, same-code distinct contexts, canonical ordering, supplier multiplicity, cache reuse/invalidation/isolation, supplied-vector provenance, reordered batch responses, CSR alignment, invalid dimensions/nonfinite outputs, overlength input, timeout/cancellation, partial outcomes and exactly one inference per unresolved unique input. Check that all-pairs execution reuses prepared vectors and a no-path run performs no inference. Keep a separate documentation review checklist for this design-only task; these are future implementation tests, not executed tests.
5. Validate the chosen model using real manufacturing descriptions, including code renaming, specification/grade changes, supplier changes, controlled unit-cost changes and altered neighbour identities/directions. Record attribute/structure scales and downstream correspondence results, without asserting proportional financial sensitivity or causal proof. Test the configured CPU path and any supported GPU/provider paths with declared embedding tolerances, truthful fallback and separate inference/runtime benchmarks. Preserve the fixed FGW fixture and its independent CPU/POT checks when validating an integrated solver; model-quality tests do not replace numerical regression.
6. Add native frontier and FGW bridges as separate stages. Run the applicable native device tests, CPU parity fixtures/tolerances and FGW intermediate/independent CPU/POT validation before describing acceleration as available. Establish bridge packaging, supported runtime/device capabilities and lifecycle tests; report unavailable prerequisites explicitly.
7. Only after correctness, add bounded all-pairs scheduling and resource reuse, and measure performance. A session may reuse one left tree while processing its remaining right partners, but this is an internal optimisation: every planned unique pair still executes, and no fixed-baseline selection replaces all-pairs semantics. Keep the independent workflow contract stable.
