# Occurrence-context embedding implementation

Parent: [Main analysis design](Main_Analysis_Design.md). Step 4 consumes final production occurrence trees and supplies vectors to [FGW](FGW_Algorithm_Design.md). Tree construction and numerical solvers do not perform model inference. Existing supplied-vector endpoints retain their contracts. The [embedding tests](Embedding_Test_Case.md) define ordinary preparation checks and a real-model smoke check; existing validation requirements remain in the parent.

## Occurrence-context embedding preparation

**Inputs:** Final inspected occurrence trees for both periods, verified material descriptions and supplier/unit-cost evidence, optional supplied vectors with provenance, configured model/revision, template and normalisation policy, cache and independent inference execution policy.

**Outputs:** One finite 384-dimensional vector for each resolved occurrence, `[nodeCount, 384]` arrays in final CSR order, occurrence-to-context mappings, context/source hashes, model/template/normalisation/precision metadata, missing-input statuses and preparation counts/timings. The model produces 384 values from the input description; callers do not provide 384 business attributes.

All twelve fields participate in the `MATERIAL_CONTEXT_V1` input. Neighbour fields are aligned lists of tuples, not a single arbitrarily chosen neighbour:

| Field | Source and interpretation |
| --- | --- |
| Material code | The current occurrence's `materialId`, scoped by dataset namespace. Include it in the model input as requested; code spelling does not establish material similarity. |
| Material name | Verified description for this material in the run's loaded snapshot. |
| Specification | Verified specification text; preserve significant sizes, grades and units. |
| Supplier | Explicit supplier evidence for this occurrence's contributing issues/output. Preserve a deterministically ordered supplier list when several suppliers contribute; do not select one without evidence. An in-house source requires an explicit source-kind declaration. |
| Category | Verified material category/type/group under a documented source mapping. |
| Unit cost | Verified decimal unit cost with currency, quantity unit, cost scope and valuation basis. Serialize the exact supplied decimal using a canonical format. Any derivation requires an explicit amount/positive-quantity basis and decimal rounding rule; do not infer it from an arbitrary purchase or substitute a different cost scope. |
| Upstream node codes | Direct incoming material neighbours in the final material-to-receiving-occurrence CSR. Retain neighbour occurrence IDs alongside codes. |
| Upstream node names | Verified names aligned with the upstream codes and occurrence IDs. |
| Upstream node specifications | Verified specifications aligned with the same upstream tuples. |
| Downstream node codes | Direct outgoing receiving neighbours in the same CSR, with occurrence IDs. |
| Downstream node names | Verified names aligned with the downstream codes and occurrence IDs. |
| Downstream node specifications | Verified specifications aligned with the same downstream tuples. |

Supplier and unit-cost evidence is not established by the present material master/purchase models. `contextEvidence` is proposed caller-supplied evidence keyed by final occurrence ID, with supplier records, a declared unit-cost basis and source references; material descriptions may also be supplied with provenance where the warehouse lacks them. Root products require their own descriptions, declared source kind and unit-cost evidence. Do not assign the root a child's supplier or price. A missing supplier/cost/description is an explicit missing field, not an invented value. A verified absence of neighbours is a valid empty list: roots normally have no outgoing receiving neighbour, and leaves have no incoming material neighbour. A boundary at direct scope does not assert that no upstream production exists outside that scope.

**Processing:**

1. Freeze tree identities, final indices and source context before inference. Collect roots, intermediate occurrences and leaves from both periods, including explicitly expanded source branches. Do not use the period-level inventory-ID graph or theoretical BOM to supply neighbours.
2. Join descriptions and supplier/cost evidence to each occurrence; validate scope, currency/units, source references and all twelve fields. Report `MISSING_EMBEDDING_CONTEXT` with occurrence ID and missing field paths. Conflicting source evidence produces `CONFLICTING_EMBEDDING_CONTEXT`. Retain discovery/inspection evidence and planned pairs; pairs involving unresolved occurrences do not execute.
3. Canonicalise a labelled twelve-field template. Align and deterministically sort neighbour tuples by material code/name/specification; preserve distinct occurrences and multiplicity even when codes match. Occurrence IDs remain provenance and only break ties between semantically identical tuples; they do not enter the encoded text or its content hash. Specify whitespace, escaping, decimal and supplier-list rules in the versioned template. Each valid empty neighbour list is represented explicitly. Do not add production/order/issue IDs as extra semantic attributes; keep them in provenance. Pass the whole description to one encoder, yielding 384 values; do not concatenate three 384-value neighbourhood blocks or twelve separately encoded field vectors.
4. Deduplicate identical canonical inputs within the run, then resolve valid supplied vectors and cache entries before bounded batch inference for the remainder. A cache key includes namespace, complete input hash, profile/template version, pinned model revision, resolved pooling/normalisation and inference precision. Material code alone is insufficient: supplier, unit cost or neighbours can change the input. Identical inputs may share vector storage while all occurrence identities and mappings remain separate.
5. Validate response-to-input identity, dimension, finite components and compatible provenance; copy vectors into final CSR order. Do not rely on a provider returning batches in submission order. Reject padding/truncation, zero placeholders and unsupported model output dimensions. Detect overlength input before inference and report `EMBEDDING_INPUT_TOO_LONG`; do not silently truncate any of the twelve fields. Genuine zero-norm model outputs require an explicit diagnostic and are not accepted as substitutes for missing evidence.
6. Reuse prepared vectors across every planned pair. Return supplied/cache/generated/unresolved occurrence counts, unique input count, actual inference count, batch timing, effective backend and per-occurrence provenance. A 4,950-pair workload does not imply 4,950 embedding-generation calls. Handle provider failure, timeout and cancellation explicitly without presenting incomplete vectors as successful output.

The embedding compatibility signature covers model/revision, profile/template, pooling/normalisation and precision. The new workflow must verify supplied vectors against their declared canonical input hashes; a legacy opaque `version` string alone does not prove twelve-field alignment. Missing provenance is explicit `UNVERIFIED_EMBEDDING_PROVENANCE`. The workflow carries a richer manifest while translating compatible vectors into the existing `version`/`values` solver input; no existing solver or HTTP field is silently redefined.

`backend/src/main/resources/cuda/material_vectorisation.cu` is an existing prototype with six descriptive groups, externally supplied token outputs and separate three-block neighbourhood aggregation. It is not an integrated model service or an implementation of this twelve-field stage. Its 1,152-value aggregated output must not be passed to the 384-dimensional FGW boundary. This documentation revision does not change that prototype.

This profile intentionally makes the attribute vector context-dependent. Supplier, unit-cost or neighbour changes can alter the attribute distance even when the current material code stays the same. Neighbour identity/direction can supplement the current undirected structural distance, while topology-related changes can influence both objective components. Textual price distance is not an exact price difference or a calibrated financial weight. Preserve separate decimal cost/quantity evidence and validate model suitability and attribute/structure scale on manufacturing examples before changing `alpha`. Keep the standard FGW formula, weights, FP64 calculation, tolerances and fixed numerical fixtures unchanged.

## Inference execution and resource lifetime

The `embedding.execution` policy applies only to model inference and is independent of frontier/FGW `useGpu`/`isNvidia`. It requests `CPU`, `GPU` or `REMOTE` through a configured provider. A GPU provider must expose an explicitly supported inference runtime and configurable device; an OpenCL FGW engine does not establish OpenCL model support. Keep a local CPU generation option in implementation scope; remote service operation is an optional deployment mode. Report requested/actual inference backend, runtime/device, model revision, precision and permitted fallback reason. A remote call does not establish which device the service used unless the service reports it.

Batch only unresolved unique inputs, keep the model loaded across batches when supported, and bound inference resources. GPU throughput depends on model, token lengths, batching and device; no acceleration ratio is established by this design. Benchmark cold load, warm batch inference, cache-hit preparation and end-to-end latency separately on actual descriptions. If embedding and FGW share a device, finish preparation before pair solves or use explicit resource limits. Lower inference precision is a separately versioned configuration requiring embedding-quality and downstream comparison checks; it does not relax FGW FP64 numerical tolerances. CPU/GPU vectors need not be bitwise identical, so validate selected model/runtime parity using declared model-specific tolerances and business fixtures.
