# Computer manufacturing data generator

Requires Python 3.10 or later; no third-party packages, database, Docker or network
access is needed. Run commands from the repository root.

```sh
python3 scripts/generate_computer_manufacturing.py --output datasets/computer-manufacturing
python3 scripts/test_generate_computer_manufacturing.py --dataset datasets/computer-manufacturing
python3 -m unittest discover -s scripts -p 'test_generate_computer_manufacturing.py' -v
```

The destination must be new or empty. Generated data is excluded by the existing
`datasets/` ignore rule. All headers, product descriptions and evidence are English.
Use a different output directory for another run. The same seed and options
reproduce every generated byte; `validation.json` is written by the separate checker.

## Products, depth and production

The default catalogue contains 36 finished products: eight office desktops, eight
gaming desktops, six ultrabooks, six gaming laptops, four all-in-one computers and
four workstations. Models differ in declared tier, RAM/storage specification and
memory/storage quantities. Family modules and raw materials are shared across SKUs.

The root is level 1. Every standard product has a spine reaching level 10 and side
branches terminating at different levels, including level 2. Other module depths
are drawn randomly. `--max-depth` accepts 3..10 and caps actual depth as well.
This is a fictional vertically integrated group including semiconductor stages;
the recipes and prices are synthetic algorithm fixtures, not engineering BOMs.

Four batches per product per period produce 288 finished-product batches, plus
independently identified upstream batches. Batch sizes cycle through 20, 50 and
100 units. Upstream batches finish one day before their receivers; complete deep
lineage can therefore start before the selected period. Load the whole package,
not only issue dates inside the sales period. Each material position is issued
60% initially and 40% on a second document the following day. Every manufactured
occurrence gets its own supplying order, fully consumed by that receiving position.

## Random changes

Defaults apply to each original component position in each ACTUAL batch:

| Independent draw | Default probability | Behaviour |
| --- | ---: | --- |
| Structure | 0.03 | Insert an integration assembly if the subtree fits; otherwise add a direct mounting component beside the selected position. |
| Material | 0.04 | Substitute a different code/specification; retain an intermediate's recipe, use a different supplier and reference price for a raw alternative. |
| Leaf cost | 0.08 | Multiply purchased-leaf price by 0.8, 0.9, 1.1, 1.25 or 1.5. |

Draws are independent and may overlap. The finished-product root is stable so
same-SKU comparisons remain meaningful. Synthetic wrappers and extra mounting
components are not redrawn recursively. The COMPARABLE period uses zero anomaly
probability by default; `--baseline-scale 1` enables the same rates there.
Probabilities are per position, not per batch: deep trees can contain many events.
Material changes are labelled injected differences, not proven business causes.

```sh
python3 scripts/generate_computer_manufacturing.py \
  --output datasets/computer-alternative --seed 123 --batches 6 \
  --max-depth 10 --structure-rate 0.05 --material-rate 0.08 \
  --cost-rate 0.15 --baseline-scale 0.2 --currency NZD
```

## Files and contracts

| File | Purpose |
| --- | --- |
| `material_master.csv` | Existing material-master import columns, including supplier/source kind and reference unit cost. |
| `bill_of_material.csv` | Fixed standard recipes. Actual exceptions never rewrite this file. |
| `inventory_usage.csv` | Existing actual-issue import columns; `order_no` is receiving production ID. |
| `purchases.csv` | Existing purchase import columns; each raw issue has a traceable purchase. |
| `sales_details.csv` | Existing sales import columns; all finished output is sold at 135% of nominal cost. |
| `production_outputs.csv` | One authoritative receipt per production ID, unit, currency and cost scope. |
| `issue_evidence.csv` | Row-aligned source line IDs, positions, supplying orders/shares, purchase references and event IDs. |
| `processing_sources.csv` | Explicit local labour and overhead pools. |
| `processing_allocations.csv` | Referenced allocation of each pool to receiving positions. |
| `actual_relationships.csv` | Batch-specific actual recipe relationships, including changes. Not a replacement for the preceding-stage actual CSR. |
| `anomalies.csv` | Injected events, original positions, before/after values and price factors. |
| `batch_expectations.csv` | Depth, event count, nominal and actual cost, and exact difference per finished batch. |
| `manifest.json` | Seed, parameters, namespace, scope, depth/event counts and limitations. |
| `validation.json` | Independent data-integrity checker result. |

Amounts use `Decimal` and six decimal places with HALF_UP rounding. Local labour
is 0.75 and overhead 0.45 per output unit; their synthetic allocation policy is
equal allocation per receiving material position, with the rounding remainder on
the last position. An allocation is counted once per position, not once per split
issue. Node cost is incoming recorded material valuation plus local processing;
descendant totals are not added again. Two split issues jointly consume the entire
source output; their explicit shares sum to 1. Share is quantity/output quantity.

`inventory_usage.product_num` and `product_total_cost` repeat the full batch totals
on every issue line. Declare both as `REPEATED_TOTAL`, never sum them. The separate
output file uses `RECEIPTS`. Reference master costs are nominal; use actual issue
amount/quantity and actual output valuation for occurrence costs. Event positions
describe the pre-insertion position; `issue_evidence.event_ids` links them to final
actual positions, including the movement caused by a wrapper.

The five basic CSVs match the current import presets. Supplementary files do not
have an automatic warehouse importer: full-lineage analysis requires adapting
them into explicit production evidence. The current warehouse adapter declares
direct-consumption scope. Exported `line_id` values are synthetic and are not
database IDs. Preserve row alignment and remap them to imported issue identities;
do not assume an import retains IDs or assigns rows in export order. For this
dataset `(date, movement_no, order_no, material_no)` identifies each issue uniquely.
Directly supplied fixtures can retain the synthetic IDs as source identities.

The current upload API accepts XLSX/XLS, not CSV. Convert the five basic files
using `scripts/export_computer_import.mjs SOURCE_DIRECTORY EMPTY_OUTPUT_DIRECTORY`
with Node.js and the configured `@oai/artifact-tool` runtime. It produces typed
numeric/date cells, one sheet per file, frozen headers and `input.json` retaining
original decimal strings for independent import checks. Keep the JSON beside the
five workbooks. Dates are numeric Excel serial values with `yyyy-mm-dd` display
formatting, compatible with the application's Apache POI parser. Standard BOM
rows combine identical child codes within a parent,
matching the warehouse's unique `(bom_no, product_no, material_no)` constraint.

From `backend/`, run the actual HTTP import test and affected handler checks:

```sh
./mvnw --batch-mode --no-transfer-progress test \
  '-Dtest=*HandlerTests,ImportJobControllerTests,ComputerManufacturingImportIntegrationTest' \
  -Dcomputer.import.fixture=/absolute/path/to/xlsx/input.json -DargLine=-Xmx2g
```

Docker remains the default Java test environment: use the documented Java 21
Maven container, mount the fixture directory read-only at `/fixtures`, and pass
`-Dcomputer.import.fixture=/fixtures/input.json`. The test binds a random loopback
HTTP port, creates a separate in-memory H2 database, and replaces raw object
storage with owned memory. It uploads all five workbooks, polls job status and
compares every warehouse field to original CSV values, retaining duplicate-row
counts. Its report is `backend/target/computer-import-validation/report.json`.
It does not validate PostgreSQL migrations, real MinIO or browser interactions.
The backend defaults to a 20 MB file limit and a 25 MB multipart request limit;
configure `IMPORT_MAX_FILE_SIZE` and `IMPORT_MAX_REQUEST_SIZE` as required. Keep
the reverse proxy's request limit compatible. Newly created raw staging tables
retain six decimal places, matching warehouse amounts; existing raw tables are
not rewritten by this change.

The generator does not run tree restoration, embedding inference or FGW. Quantity
and amount metadata do not directly affect fixed-vector FGW. Regenerated unit-cost
context can affect attribute distance; an FGW objective is not a monetary variance.
No returns, scrap, partial/shared supplying batches, stock balances, logistics or
missing-input scenarios are simulated. Nominal-to-actual differences are exact
aggregate controls; overlapping events are not given additive causal attribution.

## Validation scope

The tests cover zero-rate controls, default random changes, 100% draws at every
original position in both periods, deterministic exports, invalid CLI input and
preservation of existing destinations. The export checker independently sums
material amounts and allocations, reconciles source quantities/valuations/shares,
traverses explicit source orders to verify depth and cycles, and checks event,
purchase, sales and output links. It validates this package's all-to-one source
contract, not a general-purpose warehouse dataset. Backend numerical acceptance
and import/integration tests remain separate.
